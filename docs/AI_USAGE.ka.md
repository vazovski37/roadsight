# AI ინსტრუმენტების გამოყენება

## რა ინსტრუმენტი

**Claude Code** (Anthropic, მოდელი Claude Opus 5.5), Claude-ის desktop აპლიკაციიდან, ჩემს კომპიუტერზე, ფაილებთან,
ტერმინალთან და RunPod-ის API-სთან წვდომით.

## რისთვის გამოვიყენე

| ეტაპი | ვინ რა გააკეთა |
|---|---|
| იდეა და მიმართულება | იდეა (პანოპტიკური აღწერა + CPU ბიუჯეტი) ჩემია. AI-მ შეაფასა და მიუთითა ფაქტობრივ შეცდომაზე: BDD100K-ში შუქნიშნებსა და ნიშნებს instance მასკები არ აქვს. AI-მ ეს ოფიციალური კონფიგურაციების (`ins_seg.toml`, `pan_seg.toml`) წაკითხვით აჩვენა. |
| შეთავაზების მეორე ვერსია | AI-მ დაწერა ჩემი მოთხოვნით (PQ, fusion-ის დიზაინი, CPU სამიზნე, ოპტიმიზაციის კიბე, multi-task ablation). |
| მონაცემები | ოფიციალური ETH mirror აღარ მუშაობს. AI-მ მოძებნა ალტერნატიული წყაროები (Berkeley mirror + Hugging Face) და შეამოწმა, რომ ორი წყაროს ფაილები ერთმანეთს ემთხვევა. |
| კოდი | კოდის უმეტესი ნაწილი AI-მ დაწერა ჩემი დავალებით: data pipeline, მოდელი, FCOS loss, fusion, მეტრიკები, training loop, ONNX/კვანტიზაცია, benchmark, API. |
| ანალიზი და ანგარიში | AI-მ დაწერა ანალიზის სკრიპტები და ანგარიშის პირველი ვერსია. |

## როგორ გადამოწმდა AI-ს გადაწყვეტილებები

AI-ს ნათქვამი ფაქტად არ მიიღებოდა, თუ ის რაიმეთი არ შემოწმდა:

1. **მონაცემთა ფორმატი.** bitmask-ის კოდირება (R = კატეგორია, G = ატრიბუტები, B/A = ID) აღებულია BDD100K-ის
   დოკუმენტაციიდან და შემოწმებულია რეალურ ფაილზე. გარდა ამისა, instance-ის პიქსელების 95.8%-ზე სემანტიკური
   მასკა იგივე კლასს აჩვენებს (`data/bdd10k/stats.json`), ანუ ორი წყარო ერთმანეთთან თანხვედრაშია.
2. **მეტრიკები.** `tests/test_core.py`: PQ = 100 იდეალურ პროგნოზზე; FP/FN სწორად ითვლება; mIoU = 100.
   ყველაზე მნიშვნელოვანი ტესტი: GT სემანტიკა + GT ჩარჩოები, გატარებული ჩვენს fusion-ში, თითქმის სრულ PQ-ს იძლევა.
   ეს ერთდროულად ამოწმებს GT-ის აგებას, fusion-ს და PQ-ის კოდს.
3. **COCO წონების ჩატვირთვა.** შემოწმდა, რომ ჩატვირთვის შემდეგ ზუსტად ის ფენები რჩება ცარიელი, რაც ახალი უნდა
   იყოს (8-კლასიანი classifier, C2 დონე, სემანტიკური head) და სხვა არაფერი.
4. **ONNX export.** ONNX-ისა და PyTorch-ის გამოსავალი შედარდა: პიქსელების 100% ემთხვევა, score-ების სხვაობა ~1e-6.
   ONNX-ის შეფასებამ იგივე მეტრიკები მოგვცა, რაც PyTorch-მა.
5. **ყველა training ვარიანტი** (distillation, pruning, uncertainty weighting, single-task, MobileNet) ჯერ
   ლოკალურად, CPU-ზე, რამდენიმე იტერაციით გაეშვა, GPU-ს დაქირავებამდე.
6. **CPU ბენჩმარკი.** P-ბირთვები ექსპერიმენტით დადგინდა: 0–15 ლოგიკური CPU ~2-ჯერ სწრაფია, ვიდრე 16–31.

## სად შეცდა AI და როგორ გასწორდა

- multiprocessing-ის worker-ები Windows-ზე მთელ PyTorch-ს ტვირთავდნენ და მეხსიერება (page file) ამოიწურა.
  გამოსავალი: label/metric კოდი torch-ისგან დამოუკიდებელ მოდულებში გადავიდა (`labels.py`, `scoring.py`).
- pruning-მა channels_last ფორმატის წონებზე შეცდომა მისცა. გამოსავალი: pruning ფორმატის შეცვლამდე ხდება.
- FP16 კონვერტაციამ ტიპურად არათანმიმდევრული გრაფი შექმნა `Cast` კვანძებთან; ეს ოპერაციები ახლა FP32-ში რჩება.
- pod-ზე პირველი setup-ის გაშვება ჩავარდა (ფაილი stdin-ის გარეშე გადაიწერა). ეს შემოწმებით გამოჩნდა და ხელახლა
  გაეშვა.
- MLflow-ის SQLite ბაზაზე სამმა პარალელურმა run-მა ერთდროულად migration გაუშვა, ამიტომ ზოგი run-ის ჩაწერა
  გამოითიშა (training არ შეჩერებულა). საბოლოოდ MLflow-ში ყველაფერი ფაილებიდან შეიტანება
  (`tools/log_to_mlflow.py`).
- INT8 კვანტიზაციამ ავტომატურად box-ების decode-იც (Concat/Add/Mul) დააკვანტა: ერთი uint8 სკალა 0..W პიქსელზე
  ~2.5 პიქსელის ბიჯს ნიშნავს, mAP 4.2-ით დაეცა. AI-მ ეს val-ზე შედარებით აღმოაჩინა; ახლა prediction conv-ების
  შემდეგ ყველაფერი FP32-ში რჩება (`tools/quantize.py`), ხოლო "naive" ვარიანტი შედარებისთვის დარჩა.
- COCO-ს წონები "lite" head-ებში ზომის შეუსაბამობის გამო არ იტვირთებოდა. ახლა იტვირთება მხოლოდ ის, რაც ემთხვევა,
  და assert ამოწმებს, რომ backbone სრულად ჩაიტვირთა.
- `py-cpuinfo` AVX-VNNI-ს ვერ ხედავს (CPUID leaf 7.1-ს არ კითხულობს), ამიტომ ბენჩმარკი თავიდან "False"-ს წერდა.
  ახლა წერია "unknown".
- FP16 კონვერტაციამ (`onnxconverter_common`) R50 მოდელზე 17 GB RAM დაიკავა და კომპიუტერი თითქმის გაჭედა;
  AI-მ პროცესი გააჩერა. CPU-ზე FP16-ის გაზომვა არ შედგა (წინასწარ ისედაც ველოდით, რომ CPU-ზე არ აჩქარებს).
- AI-მ PyTorch-ის საორიენტაციო გაზომვა სხვა `--frames`-ით გაუშვა, `benchmark.py`-მ კი სხვა პროტოკოლის ძველი
  შედეგები ჩუმად გადააგდო (34 მოდელის `results/latency.json` დაიკარგა). ყველა მოდელი თავიდან გაიზომა იმავე
  პროტოკოლით, ხოლო `benchmark.py` ახლა ასეთ შემთხვევაში შეცდომით ჩერდება.
- ერთ ვიზუალიზაციაზე AI-მ თქვა, რომ ავტობუსის პიქსელები არ გაფერადდა. პიქსელების შემოწმებით აღმოჩნდა, რომ
  ბოქსის 68% სწორად არის "bus"; უბრალოდ Cityscapes-ის მუქი ფერი ყვითელ ავტობუსზე ცუდად ჩანს.
